## What is CI/CD?

CI/CD is a collection of practices and automation techniques used to continuously integrate code changes, test applications, and deliver software.

A typical CI/CD workflow is:

```text
Developer
    ↓
Write Code
    ↓
Git Repository
    ↓
Continuous Integration
    ↓
Build
    ↓
Automated Tests
    ↓
Artifact
    ↓
Deployment
    ↓
Production
```

---

## Continuous Integration (CI)

Continuous Integration is the practice of frequently integrating code changes into a shared repository.

Whenever developers push code, automated processes can:

1. Retrieve the latest code.
2. Install dependencies.
3. Build the application.
4. Run automated tests.
5. Report the result.

### Benefits of CI

* Detects bugs early
* Reduces integration problems
* Automates testing
* Improves code quality
* Provides faster feedback
* Reduces manual work

---

## Continuous Delivery

Continuous Delivery means keeping the application in a deployable state.

After code passes automated tests, the application is prepared for deployment.

A production deployment may still require manual approval.

```text
Code
 ↓
Build
 ↓
Test
 ↓
Package
 ↓
Ready for Deployment
```

---

## Continuous Deployment

Continuous Deployment goes one step further.

When code successfully passes all required checks, it is automatically deployed to production.

```text
Code
 ↓
Build
 ↓
Test
 ↓
Deploy
 ↓
Production
```

### Difference

| CI/CD Concept          | Main Purpose                           |
| ---------------------- | -------------------------------------- |
| Continuous Integration | Automatically build and test code      |
| Continuous Delivery    | Keep software ready for deployment     |
| Continuous Deployment  | Automatically deploy validated changes |

## CI/CD Pipeline

A CI/CD pipeline is a sequence of automated stages that moves code from development to deployment.

### Typical Pipeline

```text
Source Code
     ↓
Build
     ↓
Test
     ↓
Security Scan
     ↓
Package
     ↓
Deploy to Staging
     ↓
Approval
     ↓
Deploy to Production
```

---

## Common Pipeline Stages

### 1. Source

The pipeline starts when developers push code to a repository.

Examples:

* GitHub
* GitLab
* Bitbucket

### 2. Build

The application is compiled or packaged.

Examples:

* Python application → install dependencies/package
* Java application → Maven/Gradle build
* Node.js application → npm build

### 3. Test

Automated tests verify application functionality.

Examples:

* Unit tests
* Integration tests
* API tests

### 4. Security Scan

The application and dependencies can be checked for security vulnerabilities.

### 5. Package

The application is converted into a deployable artifact.

Examples:

* ZIP package
* JAR file
* Docker image
* Python package

### 6. Deployment

The application is deployed to an environment.

Examples:

* Development
* Testing
* Staging
* Production

---

## Build Artifacts

A build artifact is the output generated by the build process.

Examples:

```text
application.jar
application.zip
Docker image
Python package
compiled application
```

Artifacts can be stored and later used during deployment.

## CI/CD Environments

Most organizations use multiple environments.

```text
Development
     ↓
Testing
     ↓
Staging
     ↓
Production
```

### Development

Used by developers while building features.

### Testing

Used for automated and manual testing.

### Staging

A production-like environment used for final validation.

### Production

The live environment used by customers.

## CI/CD and Cloud Computing

CI/CD is closely connected to cloud computing.

A typical cloud deployment workflow can look like:

```text
GitHub
   ↓
CI/CD Pipeline
   ↓
Build & Test
   ↓
Cloud Deployment
   ↓
Cloud Application
   ↓
Monitoring
```

Cloud platforms provide infrastructure while CI/CD automates the process of delivering applications to that infrastructure.

* Keep pipelines automated.
* Run tests before deployment.
* Use version control.
* Protect production environments.
* Store secrets securely.
* Use separate environments.
* Monitor deployments.
* Keep pipeline configuration version controlled.
* Use small and frequent changes.
* Implement rollback strategies.
