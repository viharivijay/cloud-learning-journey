# Day 42 — Observability & Distributed Tracing 

## Overview

Observability is the ability to understand the internal state and behavior of an application or infrastructure by analyzing the telemetry it generates.

Modern cloud-native applications use observability to monitor, troubleshoot, and improve system reliability and performance.

The three primary pillars of observability are:

1. Logs
2. Metrics
3. Traces

---

## 1. What is Observability?

Observability helps engineers understand:

- What happened?
- When did it happen?
- Where did it happen?
- Why did it happen?
- Which component caused the problem?

### Basic Flow

Application → Telemetry → Observability Platform → Dashboard/Alerts → Engineer

---

## 2. Three Pillars of Observability

### 🔹 Logs

Logs are records of events generated by applications and infrastructure.

Example:

```text
2026-08-25 19:30:21
INFO: User authentication successful
````

Common log levels:

* DEBUG
* INFO
* WARNING
* ERROR
* CRITICAL

Logs help answer:

> What happened?

---

### 🔹 Metrics

Metrics are numerical measurements collected over time.

Examples:

* CPU utilization
* Memory utilization
* Disk usage
* Network traffic
* Request rate
* Error rate
* Response latency
* Availability

Example:

```text
CPU Usage: 72%
Memory Usage: 64%
Error Rate: 2.1%
Latency: 180 ms
```

Metrics help answer:

> How is the system behaving?

---

### 🔹 Traces

A trace follows a request as it travels through different services.

Example:

```text
User
 ↓
API Gateway
 ↓
Authentication Service
 ↓
Recommendation Service
 ↓
Database
```

A trace can show the time spent in each component.

```text
API Gateway          20 ms
Authentication       35 ms
Recommendation      180 ms
Database             40 ms
```

This makes it easier to identify bottlenecks.

---

## 3. Distributed Tracing

Distributed tracing is used to track requests across multiple services in a distributed application.

Example:

```text
User Request
     |
     v
API Gateway
     |
     v
Auth Service
     |
     v
ML Service
     |
     v
Database
```

The complete request represents a **trace**.

Individual operations inside the trace are called **spans**.

---

## 4. Trace vs Span

### Trace

Represents the complete journey of a request.

### Span

Represents a single operation within that trace.

```text
Trace
 |
 +-- API Gateway Span
 |
 +-- Authentication Span
 |
 +-- ML Service Span
 |
 +-- Database Span
```

---

## 5. Monitoring vs Observability

| Monitoring              | Observability                          |
| ----------------------- | -------------------------------------- |
| Detects known problems  | Helps investigate problems             |
| Usually alert-focused   | Investigation-focused                  |
| Uses predefined metrics | Uses logs, metrics, traces and context |
| "Something is wrong"    | "Why is something wrong?"              |

### Simple Definition

> Monitoring tells you that something is wrong; observability helps you understand why.

## 8. Alerting

Alerting automatically notifies engineers when predefined conditions occur.

Example:

```text
Error Rate > 5%
       |
       v
Alert Triggered
       |
       v
Engineer Notified
```

A better alert generally considers both a threshold and duration:

```text
Error Rate > 5%
for 5 minutes
       |
       v
Critical Alert
```

## 9. SLI, SLO and SLA

These concepts are important in Site Reliability Engineering (SRE).

### SLI — Service Level Indicator

A measurement of service performance.

Example:

```text
Availability = 99.95%
```

### SLO — Service Level Objective

The target for a service metric.

Example:

```text
Availability Target >= 99.9%
```

### SLA — Service Level Agreement

A formal agreement between a service provider and customer defining expected service levels.

### Relationship

```text
SLI
 |
 | Measurement
 v
SLO
 |
 | Target
 v
SLA
 |
 | Customer Commitment
 v
Agreement
```

## 11. Why Observability is Important

Observability helps organizations:

* Detect failures
* Troubleshoot applications
* Identify performance bottlenecks
* Reduce downtime
* Improve reliability
* Monitor infrastructure
* Analyze application behavior
* Detect unusual patterns

## 12. Observability in Microservices

Microservices create additional troubleshooting challenges because a single request can travel through multiple services.

Example:

```text
             Request
                |
                v
          API Gateway
          /          \
         v            v
     Auth Service   User Service
         |            |
         v            v
      Database      Database
                |
                v
          Recommendation
              Service
```

Distributed tracing helps identify which service is responsible for latency or failures.

## 14. Common Problems Observability Helps Solve

### High Latency

Metrics identify increased latency.

Tracing identifies the slow service.

Logs identify the underlying error.

### Service Failure

Metrics detect increased errors.

Tracing identifies the affected service.

Logs provide detailed failure information.

### Resource Exhaustion

Metrics can identify:

* High CPU
* High memory
* Disk exhaustion
* Network saturation

## 15. Key Interview Questions

### Q1. What is observability?

Observability is the ability to understand the internal state and behavior of a system using telemetry such as logs, metrics, and traces.

### Q2. What are the three pillars of observability?

The three primary pillars are:

1. Logs
2. Metrics
3. Traces

### Q3. What is distributed tracing?

Distributed tracing tracks a request as it travels across multiple services in a distributed application.

### Q4. What is a span?

A span represents an individual operation within a distributed trace.

### Q5. What is Open Telemetry?

Open Telemetry is an open-source framework for generating, collecting, and exporting telemetry such as logs, metrics, and traces.

### Q6. Monitoring vs observability?

Monitoring focuses on detecting known conditions, while observability provides the information needed to investigate system behavior and determine root causes.

### Q7. What are SLI, SLO and SLA?

* SLI → Actual measurement
* SLO → Desired target
* SLA → Formal customer/service agreement

### Q8. Why is distributed tracing important?

It helps identify where latency and failures occur across multiple services.
